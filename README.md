# 书架星系 · 暗物质图书馆

> 下一代图书馆，不只帮你找到书；它让你有意义地迷路。

![书架星系首屏：由真实书籍构成的暗物质图书馆](docs/hero-preview.png)

「书架星系」是一个面向普通读者的三维阅读体验原型：每一颗星是一部真实作品，书与书之间的关系被显影成可进入的航线。用户从一本熟悉的书出发，选择离熟悉程度不同的偏航方向，在星海里撞见下一本书；走过的路径最后会被压印成一张只属于这次阅读的未刊星图。

这是一个体验、两条证据链：同一套星海同时回应赛题 02「图书馆的超进化」与赛题 03「制造一点意外」。它不是把书目做成更漂亮的搜索结果，而是把图书馆从“找答案的地方”变成“发现问题与邻居的地方”。

## 一次体验，两条证据链

| 赛题 | 我们要回答的问题 | 产品中的可验证证据 |
| --- | --- | --- |
| 02 · 图书馆的超进化 | 如果图书馆不再只负责检索，下一种阅读入口是什么？ | 20,050 颗书星组成可拖拽、可缩放、可点选的三维星海；从书目卡片进入关系航线；航迹会被记录并生成星图；关系依据可以被主动查看。 |
| 03 · 制造一点意外 | 怎样让意外不是随机噪声，而是事后能解释的相遇？ | 偏航引擎主动寻找近距、中距与远距关系，缺少某一档时界面按真实惊喜度描述；当前关系以金色航线和抵达叙事显影；「馆员波段」解释连接依据，也允许用户要求一次更大胆的联想；最终留下可下载的意外证据。 |

## 3 分钟路演路径

建议使用一块普通显示器、浏览器全屏演示。整个体验不依赖 VR、外接传感器或在线大模型。

1. **0:00 — 先提出命题。** 进入页面，评委会先看到“下一代图书馆，不只帮你找到书。它让你有意义地迷路。”以及实时书星、隐藏引力统计。点击预设《三体》，或在输入框搜索一本书，按「开始偏航」。
2. **0:25 — 让评委看到规模。** 拖动星海观察三维层次，滚轮缩放；悬停会显示星点对应的书名，点选后出现作品、作者、年代、语言、主题与摘要。此时说明：这不是手工画出的有限海报，而是 20,000 本 Project Gutenberg 作品加 50 本策展书的可探索目录。
3. **0:55 — 让意外发生。** 在书籍观测台点击「从这里偏航」。底部的偏航罗盘给出三张卡片：沿着近处的回声、穿过一条隐秘暗河、去最远但仍说得通的地方。选择任意方向，镜头会沿当前关系飞行，星海中只亮起这一条航线。
4. **1:25 — 把相遇讲清楚。** 抵达下一本书后，先读关系句子，再点击「询问引力来源」。打开「馆员波段」，演示「显示依据」与「再大胆一点」：它会把主题、作者、语言或年代等依据与解释性联想分开呈现，并明确这不是文学史影响关系。
5. **2:00 — 证明这不是一次性烟花。** 再偏航一至两次，观察左侧「本次航迹」如何累积。可以切换「稳定镜头」、开启声音或进入全屏；按 `Esc` 可中止飞行，说明作品为现场交互保留了可控性与退路。
6. **2:35 — 收束故事。** 当航迹达到三本书后，书籍观测台会出现「留下这次迷路」。点击后，空间关系被压成 3200 × 1800 的纸质星图，带有航线、书名、关系句、日期与“迷路”朱印；点击「保存高清星图」即可带走本次相遇。

如果现场时间更短，保留“《三体》→偏航罗盘→抵达另一颗书星→馆员波段→星图”这一条主线即可。不要先打开 AI：AI 的出现应该由评委的好奇心召唤，而不是遮住星海。

## 核心体验

### 1. 星点是书，不是装饰

全量目录中的每一条作品记录都会得到稳定的空间位置和视觉参数。位置由书籍 ID、主题与索引经过确定性哈希计算，同一份数据每次载入都得到同一片星海。50 本策展书带有摘要、情绪、主题和可核查来源，适合现场讲述；其余目录作品保留真实书名、作者、语言、年代、主题和来源链接。

### 2. 关系只显影当前航线

全量关系不会被同时画成一团“蜘蛛网”。用户选择一本书后，系统以作者、主题、年代、语种对应的惊喜度带，从未访问的候选中各寻找近距、中距和远距关系；某一档不存在时，不会伪造距离，按钮文案会按实际关系变化。用户做出选择，当前关系才以弧线、信标和文字出现。

关系类型使用「回声、镜像、暗河、裂隙、余烬、潮汐」等叙事词，但每条关系仍保留可读的 `basis` 与 `provenance` 字段。

### 3. AI 是隐身的馆员，不是首页主持人

默认体验完全不显示聊天框，也不需要 API Key。只有用户主动点击「询问引力来源」后，才会展开「馆员波段」；它先给出本地关系解释，再可选地把问题交给用户配置的 HTTP(S) 端点。没有端点、网络失败或超时，都不会破坏星海、偏航或星图。

### 4. 每一次迷路都有一个出口

用户可以关闭观测台、取消偏航、返回出发星或重置体验。三本书以上的航迹可以导出成高清星图；导出不是当前屏幕截图，而是由 Canvas 重新排版的纸面作品，适合在路演结束时作为“阅读发生过”的物证。

![三本书航迹显影成的未刊星图](docs/star-chart-preview.png)

## 视觉立场

视觉方向刻意避开廉价的赛博朋克霓虹。它把三种观看方式叠在一起：

- **天文观测台**：黑色背景、三维深度、稀薄星尘和一条被选中的航迹，邀请用户靠近而不是一次看完。
- **旧星图与暗房**：米灰纸张、墨黑文字、旧金线、翡翠灰和朱印红，把探索结果从屏幕中的“数据状态”变成可以收藏的出版物。
- **馆员的手写判断**：关系句子不是标签堆砌，而是可朗读、可追问的短叙事；证据和推测在界面上有明确边界。

三维星云、书星、尘埃和关系线由 Three.js/WebGL2 的程序化材质完成；星图由 Canvas 2D 重新绘制。当前版本不依赖外部图片、封面或在线字体服务，避免加载失败把核心体验变成空白。

## 数据规模与关系边界

当前提交快照包含：

| 层级 | 数量 | 用途 | 可信边界 |
| --- | ---: | --- | --- |
| Project Gutenberg 目录作品 | 20,000 | 全量星海中的真实作品节点 | 来自官方离线目录的 `Type=Text` 记录；按规范化题名 + 作者去重，保留一个代表记录。 |
| 策展书目 | 50 | 中文路演入口与可讲述的作品卡片 | 书名、作者等可通过 Open Library 检索页核查；这些卡片不是图书馆真实馆藏。 |
| 目录关系 | 60,000 | 让 20,000 个目录节点可持续漫游 | 由共享主题、主题词、作者、语言和年代分组稳定生成；关系依据是目录元数据邻接。 |
| 策展关系 | 164 | 安娜 ↔ 艾玛、三体 ↔ 基地等高叙事密度的连接 | 人工撰写的阅读联想，字段中标记为 `reading-hypothesis`。 |
| 应用展示总量 | 20,050 本书 / 60,164 条关系 | 首屏统计和运行时图谱 | 50 本策展书与 164 条策展关系叠加到目录快照上。 |

数据快照由 `scripts/build-catalog.mjs` 构建，当前 `public/data/manifest.json` 记录的生成时间是 `2026-08-23T00:00:00.000Z`，目录文件 SHA-256 为 `55b5bc0a2d99875e8cfcda42e5ddedef31625c0344491c189de302a2995c1b5f`。快照同时覆盖 27 种语言。目录原始 CSV 没有下载次数，所以 `downloads` 明确为 `null`，不会把“未报告”伪装成“0”。

### 关系不是文学史事实

这是作品最重要的诚实边界：

- 目录关系中的“主题：……”或“语言：……”是**来源数据提供的共同字段**；系统据此构成一条可探索的元数据邻接，不等于两位作者互相影响。
- 策展关系中的句子是**阅读联想与产品叙事**，不是研究结论，也不声称存在引用、改编或文学史上的因果关系。
- 界面里的「书目事实」只指作品书目字段或目录共同字段；「阅读联想」与「语义推断」代表解释层，不能混读。

这种边界让“意外”可以大胆，但不需要靠伪造权威来成立：评委看到的是一条被标注过的阅读路径，而不是把猜测包装成知识。

### 数据来源与许可

目录输入是 [Project Gutenberg Offline Catalogs](https://www.gutenberg.org/ebooks/offline_catalogs.html) 的 [官方 `pg_catalog.csv.gz`](https://www.gutenberg.org/cache/epub/feeds/pg_catalog.csv.gz)。项目只提交目录字段和作品页面链接，不重新分发 Gutenberg 正文；适用条款、商标与再分发注意事项见 [data-sources.md](data-sources.md)。策展书目的来源链接在 `src/data/curatedBooks.ts` 中逐条保存。

## AI 边界：离线核心，在线增强

### 离线即可完成的部分

- 三维星海渲染、拖拽/缩放/悬停/点选。
- 20,050 本书的载入与本地关系解析。
- 三种偏航方向、镜头飞行、关系线、抵达叙事和航迹记录。
- 本地“馆员波段”的关系依据、阅读联想与边界提示。
- 声音开关、稳定镜头、全屏、`Esc` 中止飞行和 3200 × 1800 星图导出。

### 可选的在线增强

只有配置 `VITE_AI_ENDPOINT` 后，馆员波段才会显示追问输入框。应用向该端点发送当前问题、出发书、抵达书、关系句、关系依据和最近五本航迹，期待收到如下最小响应：

```json
{ "answer": "一段不超过 900 个字符的解释" }
```

前端会限制问题为 240 个字符，并在 8 秒后超时；它不会在浏览器中保存或暴露模型私钥。这里没有把远程模型宣称为 60,000 条关系的来源：全量图谱是可复现的本地数据，在线 AI 只负责在用户主动追问时增加一层开放式解释。

`.env` 不应提交到仓库。可参考下面的本地配置：

```dotenv
VITE_AI_ENDPOINT=https://your-domain.example/api/curator
```

## 技术架构

```text
React 19
  ├─ App + experienceReducer       体验状态、航迹、取消与错误边界
  ├─ ExperienceUI                  入口、观测台、偏航罗盘、馆员波段、星图
  └─ GalaxyCanvas
       └─ GalaxyEngine             Three.js/WebGL2 原始渲染、拾取、飞行、释放资源

静态数据
  ├─ curatedBooks / curatedRelations / demoJourneys
  ├─ public/data/catalog.json      20,000 本书 + 60,000 条目录关系
  └─ loadGalaxy.ts                 规范化、邻接索引、关系解释与三方向选择

离线工具
  ├─ scripts/build-catalog.mjs     下载/读取官方 CSV，去重、生成关系、写 manifest
  └─ scripts/check-catalog.mjs     计数、ID、重复作品、关系完整性与 SHA 校验
```

渲染层使用一个书星 `BufferGeometry` 承载全量节点，配合程序化星云和受控的当前关系线；React 只管理交互状态，不为每颗星创建一个 DOM 节点。位置和选择排序使用确定性哈希，便于路演复现与数据检查。WebGL 上下文丢失、窗口尺寸变化、动画取消和 Three.js 资源释放均有处理。

## 本地运行

需要 Node.js `20.19+` 或 `22.12+`。当前开发环境使用 Node.js `v24.14.1`、npm `11.11.0`。

```bash
npm ci

# 开发服务器，默认打开 http://localhost:5173
npm run dev

# 生产构建
npm run build

# 预览生产构建
npm run preview

# 单元测试
npm test

# 一次完成测试 + TypeScript 构建 + Vite 构建
npm run check
```

首次打开时，应用先以 50 本策展书显影，然后载入静态目录；目录加载失败会保留策展体验并明确进入 fallback 状态，不会显示伪造的全量数字。生产构建的静态文件输出到 `dist/`，该目录已被 `.gitignore` 排除。

## 数据重建与验证

默认构建器会使用本地 `data/raw/pg_catalog.csv`；若本地没有输入，会从官方地址下载并缓存原始 CSV。原始文件被 `.gitignore` 排除，不会随仓库提交或进入 `dist/`。

```bash
# 使用已有缓存重建默认快照（20,000 本 / 60,000 条关系）
npm run build:data

# 完全离线地使用指定 CSV
node scripts/build-catalog.mjs --input path/to/pg_catalog.csv

# 固定生成时间，便于复现 manifest
node scripts/build-catalog.mjs --generated-at 2026-08-23T00:00:00Z

# 校验提交快照
npm run check:data
```

校验脚本会确认书籍数量至少 20,000、关系数量至少 50,000，检查书籍 ID 唯一、题名+作者去重、来源 URL、主题数组、关系无自环/悬空/重复，并重新计算 `catalog.json` 的 SHA-256。当前快照的验证结果为 20,000 本、60,000 条关系、27 种语言。

## 静态部署

本项目没有后端依赖，部署目标只需要支持静态文件和较大的 JSON 资源。

```bash
npm ci
npm run check
# 将 dist/ 上传到 GitHub Pages、Cloudflare Pages、Netlify 或任意静态站点
```

在 GitHub Pages 中可使用 GitHub Actions：构建任务执行 `npm ci` 与 `npm run build`，再把 `dist/` 作为 Pages artifact 发布。Vite 已设置 `base: './'`，适合仓库项目子路径；如果改为挂载在固定绝对路径下，再按托管平台调整 `base`。在线馆员端点应作为部署环境变量注入，不能把服务端模型密钥写入前端仓库。

## 未来馆藏适配接口

当前 Demo 使用 `public/data/catalog.json` 静态快照，没有连接任何图书馆真实数据库。仓库已经提供纯函数 `normalizeLibraryRecord()`（`src/data/libraryAdapter.ts`）：它可接收常见中英文字段的 CSV/JSON 馆藏记录，校验题名、作者与 HTTPS 来源，为 ISBN、书目记录号或题名/作者组合生成稳定 ID，再输出应用可直接使用的 `Book`。真正接入馆藏时，只替换数据适配层，不需要改动星海和体验层。

批量快照与关系层应继续遵守下面的数据契约：

```ts
type LibrarySnapshot = {
  generatedAt: string
  source: string
  sourceUrl: string
  books: Array<{
    id: string                 // 馆藏系统稳定 ID；不要用显示标题代替
    title: string
    author: string
    year?: number
    language?: string
    subjects?: string[]
    themes?: string[]
    source?: string
    sourceUrl?: string
  }>
  relations: Array<{
    source: string
    target: string
    kind?: '回声' | '镜像' | '暗河' | '裂隙' | '余烬' | '潮汐'
    weight?: number
    basis?: string[]
    provenance?: 'catalog' | 'semantic' | 'reading-hypothesis'
  }>
}
```

适配时需要保留三条规则：一是版本、借阅记录与作品本体分开，避免同一本书因译本变成多颗星；二是任何关系都要能说明依据或标注为推测；三是没有关系数据时可以先用主题/分类生成邻接，但必须把它标为书目推断，而不是文学史事实。未来可在 `src/data/loadGalaxy.ts` 前增加馆藏 adapter，把馆藏 API、导出文件或定期快照统一成上述形状。
